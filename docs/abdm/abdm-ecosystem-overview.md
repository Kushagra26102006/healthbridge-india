# ABDM Ecosystem Overview — HealthBridge India

## 1. Core Architectural Distinction
A **clinical record-storing platform** (such as HealthBridge India's current internal Patient, Doctor, Pharmacy, and Laboratory portals) stores electronic health data inside its own application database for direct tenant access. By contrast, an **ABDM federated exchange participant** connects to India's National Digital Health Ecosystem via the **data-blind HIE-CM Gateway**, exchanging encrypted HL7 FHIR R4 clinical documents across independent healthcare facilities **only** upon explicit, digitally signed, purpose-limited patient consent.

## 2. ABDM Ecosystem Concepts & Relevance to HealthBridge India

| Concept | Definition (Verified from Official ABDM/NHA Docs) | Primary Participants | Relevant to HealthBridge? | Official Integration / Onboarding Requirements | Workflows / APIs Involved | What Remains Unverified |
|---|---|---|---|---|---|---|
| **ABHA Number** | Unique 14-digit national health identifier for Indian citizens (`XX-XXXX-XXXX-XXXX`) issued by NHA. | Citizens / Patients, M1 Health Systems | **Yes (Milestone 1)** | Sandbox registration (`sandbox.abdm.gov.in`), M1 functional certification, explicit citizen consent for KYC/Aadhaar/DL. | ABHA V3 APIs (`https://abhasbx.abdm.gov.in/abha/api/v3`) — enrollment, OTP/biometric verification. | Exact current ABHA V3 field schemas & RSA public key rotation endpoints (requires portal login). |
| **ABHA Address** | Human-readable PHR identifier (e.g., `name@abdm` in prod, `name@sbx` in sandbox) linked to an ABHA Number. | Patients, HIPs, HIUs, HIE-CM | **Yes (M1/M2/M3)** | M1 verification; used as patient identifier in linking and consent discovery. | ABHA V3 verification, Scan & Share, HIE-CM linking. | Current PHR suffix validation rules in sandbox vs production. |
| **Health Information Provider (HIP)** | Healthcare facility system that generates, stores, and shares patient health records upon consent. | Hospitals, Clinics, Diagnostic Labs (HealthBridge Doctor & Lab portals) | **Yes — Proposed (Milestone 2)** | HFR Facility ID, M2 bridge registration, public HTTPS callbacks, NRCeS FHIR R4 compliance, Fidelius encryption. | Care Context linking, discovery (`discover`/`on-discover`), consent notify, encrypted data transfer. | Exact V3 HIP OpenAPI specs & sandbox test cases inside developer portal. |
| **Health Information User (HIU)** | Healthcare software that requests and views longitudinal records from external HIPs with patient consent. | Treating Doctors, Hospitals (HealthBridge Doctor portal) | **Yes — Proposed (Milestone 3)** | HIU role approval, HIE-CM callback registration, Fidelius decryption, clinician viewer. | Consent request (`consent-requests/init`), `on-notify`, HI request, encrypted data ingestion. | Current V3 HIU callback error codes & signature verification public key endpoints. |
| **Health Facility Registry (HFR)** | National repository of verified public and private healthcare facilities (clinics, labs, hospitals, pharmacies). | Healthcare Facilities | **Yes (Prerequisite for M2/M3)** | Facility registration on HFR portal or via M4 APIs; required to obtain Facility ID. | HFR Facility ID mapping to `Organization.identifier` (`https://facility.ndhm.gov.in`). | Current M4 programmatic HFR API eligibility rules. |
| **Healthcare Professionals Registry (HPR)** | National repository of verified healthcare professionals (doctors, pathologists, nurses). | Doctors, Pathologists | **Yes (Recommended)** | Practitioner verification on HPR; links `Practitioner.identifier` (`https://doctor.ndhm.gov.in`). | HPR profile verification & FHIR `Practitioner` attribution. | M4 HPR integration sandbox approval prerequisites. |
| **Consent Manager / HIE-CM** | Data-blind national gateway orchestrating consent requests, consent artefacts, discovery, and routing between HIPs and HIUs without storing clinical payloads. | All HIPs, HIUs, PHR Apps | **Yes (Core Integration Hub)** | Client ID/Secret via ABDM Sandbox, `X-CM-ID` header (`sbx` in sandbox), V3 Sessions auth. | `POST /api/hiecm/gateway/v3/sessions`, asynchronous `REQUEST-ID` + `on-*` callbacks. | Exact production `X-CM-ID` values and bridge throttling quotas. |
| **Health Records Discovery & Linking** | Process by which a patient's Care Contexts (OPD visit, lab order/report) are matched and linked to their ABHA Address. | HIPs, PHR Apps, HIE-CM | **Yes (Milestone 2)** | Care Context grouping per encounter/order; supports both HIP-initiated and user-initiated linking. | `discover`, `link/init`, `link/confirm`, `add-contexts`. | Exact V3 Care Context payload schemas (account-gated OpenAPI). |
| **Consent Artefact** | Digitally signed electronic contract from HIE-CM specifying patient, purpose code, HI-types, date range, expiry (`dataEraseAt`), and revocation status. | HIE-CM, HIPs, HIUs | **Yes (Critical Control)** | Must verify signature, active status, expiry, revocation, HI-type, and date range before any transfer. | `consents/hip/notify`, `consents/hiu/notify`, `consents/fetch`. | Exact JWS/digital signature verification key format in V3. |
| **FHIR R4 Representation & Fidelius Encryption** | NRCeS ABDM FHIR R4 Document Bundles (`Composition` + linked resources) encrypted end-to-end via ECDH Curve25519 (short Weierstrass) + HKDF-SHA256 + AES-256-GCM. | HIPs, HIUs | **Yes (M2 & M3)** | Validate against NRCeS `ndhm.in` package (v6.5.0+); use BouncyCastle-compatible Weierstrass Curve25519 parameters. | Data Push URL transfer & acknowledgement. | Live gateway decryption verification against NHA sandbox HIU/HIP simulator. |
